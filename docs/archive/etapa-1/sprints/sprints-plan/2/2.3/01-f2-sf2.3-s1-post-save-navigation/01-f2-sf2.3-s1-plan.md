## 3. Alcance del Sprint

### Qué debe conseguir este Sprint
1. **handleSubmit (create)**: Tras crear un prompt nuevo, redirigir a `/prompts/[nuevo-id]` en modo edición (no volver a `/prompts`)
2. **handleSubmit (edit)**: Tras editar un prompt existente, permanecer en `/prompts/[id]` (actualmente ya funciona, pero el `router.push("/prompts")` expulsa al usuario)
3. **handleDuplicate**: Tras duplicar un prompt, redirigir al nuevo prompt duplicado en `/prompts/[nuevo-id]` en modo edición
4. **handleDelete**: Tras eliminar un prompt, redirigir a `/prompts` (este comportamiento se mantiene — no hay prompt que editar tras borrar)

### Qué NO entra en este Sprint
- Cambios en API routes (ya retornan el prompt creado con ID)
- Cambios en schema o migraciones
- Cambios en PromptList, PromptFilters u otros componentes
- Modificación de la lógica de guardado, validación o payload
- Implementación de SF-3.1 (vista lista) o SF-3.2 (filtros multi-selección)

## 5. Plan de acción

### Acción 1: Modificar `handleSubmit` para create mode
**Archivo**: `components/prompt/PromptForm.tsx`  
**Ubicación**: Línea ~202 (`router.push("/prompts")`)

**Cambio**:
- Tras `response.ok` en modo create (`!prompt`), obtener el ID del prompt creado desde la respuesta de la API
- Redirigir a `/prompts/${newId}` en lugar de `/prompts`
- Mantener `router.refresh()` para actualizar datos del server

**Implementación**:
```typescript
// Actualmente:
if (response.ok) {
  router.push("/prompts")
  router.refresh()
}

// Cambiar a:
if (response.ok) {
  const result = await response.json()
  if (!prompt && result.data?.id) {
    router.push(`/prompts/${result.data.id}`)
  } else {
    router.refresh()
  }
}
```

**Nota**: La API POST ya retorna `{ data: prompt }` con el objeto completo incluyendo `id` (`route.ts:238`). La API PUT no necesita redirección (permanece en la misma ruta), solo `router.refresh()`.

### Acción 2: Modificar `handleDuplicate` para redirigir al nuevo prompt

**Cambio**:

## 6. Validación y pruebas

### Qué debe validarse
1. **Create → edición**: Crear un prompt nuevo → guardar → verificar que la URL cambia a `/prompts/[id]` y el formulario muestra acciones de edición (Duplicate, Delete)
2. **Edit → permanencia**: Editar un prompt existente → guardar → verificar que la URL se mantiene en `/prompts/[id]` y el formulario sigue visible
3. **Duplicate → edición**: Duplicar un prompt → verificar que la URL cambia a `/prompts/[nuevo-id]` y el formulario muestra el prompt duplicado en modo edición (título con " (Copy)")
4. **Delete → listado**: Eliminar un prompt → verificar que la URL cambia a `/prompts` (comportamiento existente, sin cambios)

### Mecanismos existentes
- `npm run build`: Verificación de compilación Next.js
- `npm run lint`: ESLint
- `npm test`: Jest + React Testing Library (40 tests existentes)

## 7. Seguridad y no regresión

### Qué debe preservarse
- Auth check en handlers: `useSession()` ya protege el componente (no cambia)
- Ownership check en API: `[id]/route.ts` mantiene `checkOwnership` para PUT/DELETE
- Zod validation: schemas de create/update no se modifican
- CSRF protection: NextAuth v5 built-in (no cambia)

### Qué debe revisarse
- Que `response.json()` no falle si la API retorna un formato inesperado (fallback a `/prompts`)
- Que `router.push()` se ejecute solo tras `response.ok` (ya garantizado por el `if`)

### Riesgos de regresión
| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| `response.json()` falla si API no retorna `data.id` | BAJA | MEDIA | Fallback a `/prompts` en el `else` |
| `router.push` con ID incorrecto | BAJA | ALTA | Verificar que API retorna `data.id` correctamente |
| Tests existentes fallan | BAJA | MEDIA | Ejecutar `npm test` antes de commit |

## 9. Riesgos o advertencias

### Incidencias previsibles
1. **Formato de respuesta API**: Si la API POST cambia su formato de respuesta (`{ data: prompt }` → otro), el `result.data?.id` podría ser undefined. Mitigación: fallback a `/prompts` en el `else`.
2. **Race condition con `router.refresh()`**: Si `router.push` y `router.refresh` se ejecutan simultáneamente, podría haber un flicker. Mitigación: en create/duplicate, usar solo `router.push` (el server component recargará los datos al navegar).

### Dependencias sensibles
- **API POST debe retornar `data.id`**: Ya lo hace (`route.ts:238`: `return NextResponse.json({ data: prompt }, { status: 201 })`). Si esto cambia, el Sprint se bloquea.
- **PromptForm usa `prompt?` para distinguir create/edit**: Ya implementado (`PromptForm.tsx:59`). No cambia.

### Limitaciones
- Este Sprint solo modifica la navegación del formulario. No aborda SF-3.1 (vista lista) ni SF-3.2 (filtros multi-selección), que son Subfases de Fase 3.
- La preferencia de visualización del listado (RF-39, RF-40) no entra en este Sprint.
