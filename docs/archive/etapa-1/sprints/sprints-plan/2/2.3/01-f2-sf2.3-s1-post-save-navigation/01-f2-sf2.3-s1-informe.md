## 2. Objetivo original del Sprint

Modificar los 3 handlers de navegación en `PromptForm.tsx` para que:
- El usuario permanezca en el formulario tras guardar (alta/edición)
- El usuario sea redirigido al nuevo prompt tras duplicar
- El usuario vuelva al listado solo tras eliminar un prompt

En lugar del comportamiento anterior que siempre redirigía a `/prompts` tras cualquier operación.

## 3. Alcance realmente ejecutado

### ✅ Qué se consiguió finalmente
1. **handleSubmit (create)**: Tras crear un prompt nuevo, redirige a `/prompts/[nuevo-id]` en modo edición
2. **handleSubmit (edit)**: Tras editar un prompt existente, permanece en `/prompts/[id]` con `router.refresh()`
3. **handleDuplicate**: Tras duplicar un prompt, redirige a `/prompts/[nuevo-id]` del prompt duplicado
4. **handleDelete**: Mantiene comportamiento existente — redirige a `/prompts` tras eliminar

## 12. Conocimiento técnico reutilizable

### Patrón de navegación condicional en App Router
**Contexto**: Next.js 14 App Router con `router.push()` y `router.refresh()`

**Lección aprendida**:
- En modo create: usar `router.push(`/prompts/${id}`)` sin `router.refresh()` — el server component recargará los datos automáticamente al navegar a la nueva ruta
- En modo edit: usar solo `router.refresh()` sin `router.push()` — permanece en la misma ruta y recarga datos del server
- La API debe retornar `{ data: { id: string } }` para permitir la redirección post-create

**Código de referencia**:
```typescript
// Create mode:
if (!prompt && result.data?.id) {
  router.push(`/prompts/${result.data.id}`)
} else {
  router.refresh()
}

// Duplicate mode:
if (result.data?.id) {
  router.push(`/prompts/${result.data.id}`)
} else {
  router.push("/prompts")
}
```

### Fallback defensivo en redirección
**Lección**: Siempre incluir fallback a `/prompts` en caso de que `result.data?.id` sea undefined, para evitar redirecciones rotas.
