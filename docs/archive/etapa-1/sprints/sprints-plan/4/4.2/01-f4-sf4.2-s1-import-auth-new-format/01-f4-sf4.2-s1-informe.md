## 3. Alcance realmente ejecutado

### ✅ Qué se consiguió finalmente

1. **Auth check implementado**: Función `auth()` importada desde `@/lib/auth` y ejecutada como PRIMERA operación antes de cualquier acceso a DB (patrón validado en SF-4.1-S1)
2. **Respuesta 401 sin autenticación**: Endpoint retorna `{ error: "Unauthorized" }` con status 401 cuando no hay sesión válida
3. **Filtrado por userId garantizado**: Todos los prompts importados se asignan al `userId` del usuario autenticado; upsert solo opera dentro del mismo userId (aislamiento de datos)
4. **Detección de formato implementada**: Campo `version` del JSON determina si se usa parser v2.0 o v1.0
5. **Parser v2.0 funcional**: Procesa arrays de nombres para 6 relaciones N:M (platforms, categories, clientProjects, useCases, modelHints, tags); hace upsert de entidades relacionadas si no existen; crea relaciones en junction tables usando `$transaction`
6. **Parser v1.0 funcional (compatibilidad)**: Procesa campos legacy (platform, clientOrProject, useCase, modelHint como strings simples); mismo comportamiento que antes pero con auth + userId añadidos
7. **Upsert por coincidencia (D-02)**: Si prompt importado coincide con existente (mismo userId + ID o mismo userId + título), se reemplaza el existente; si no coincide, se crea nuevo
8. **Normalización de nombres (D-06)**: Funciones auxiliares `normalizeName()` y `createSlug()` implementadas para prevenir duplicados por case (trim + lowercase)
9. **Transaccionalidad (D-07)**: Todas las operaciones de delete+create en junction tables usan `$transaction` para atomicidad
10. **Validación Zod estricta**: Schemas separados para v1.0 y v2.0 con tipos específicos

## 8. Incidencias detectadas

### Incidencia 1: Campo `category` en formato v1.0

- **Qué ocurrió**: El schema v1.0 original intentaba usar `categoryId` directamente, pero el formato de import v1.0 usa `category` (nombre string), no `categoryId`
- **Cuándo se detectó**: Durante implementación del parser v1.0
- **Impacto**: Los imports antiguos no funcionarían correctamente
- **Cómo se resolvió**: El parser v1.0 ahora usa `categoryMap` para resolver nombres de categorías a IDs, igual que el código original. Además, se actualiza el `categoryId` del prompt después de crearlo/actualizarlo.

### Incidencia 2: Complejidad de funciones auxiliares

- **Qué ocurrió**: Las funciones `upsertEntity`, `upsertCategory`, `upsertTag` requieren acceso dinámico a modelos de Prisma
- **Cuándo se detectó**: Durante implementación
- **Impacto**: TypeScript puede tener problemas con tipos dinámicos
- **Cómo se resolvió**: Se usó indexación dinámica `prisma[entityType as any]` con types casting. Funciona correctamente pero requiere revisión de tipos en build.

## 9. Correcciones y ajustes aplicados

### Ajuste 1: Manejo de fechas en importación

- **Original**: Plan no mencionaba serialización de fechas
- **Ajuste**: Se añadió manejo de `lastUsedAt` y `createdAt`/`updatedAt` como strings ISO en el schema, convirtiéndolos a `Date` solo cuando se crean/actualizan prompts
- **Justificación**: El export v2.0 serializa fechas como ISO strings; el import debe manejarlo

### Ajuste 2: Respuesta JSON detallada

- **Original**: Plan mencionaba respuesta simple
- **Ajuste**: Respuesta incluye `imported`, `upserted`, `created` counts + `format` (v1.0 o v2.0)
- **Justificación**: Mejor feedback para el usuario sobre qué ocurrió

## 12. Conocimiento técnico reutilizable

### Patrón 1: Auth check como PRIMERA operación (seguridad crítica)

**Ubicación**: `app/api/import/prompts/route.ts` líneas 473-481

```typescript
const session = await auth()
if (!session?.user?.id) {
  return NextResponse.json({ error: "Unauthorized" }, { status: 401 })
}
const userId = session.user.id
// AHORA SÍ: acceso a DB con userId verificado
```

**Lección**: Auth check debe ejecutarse ANTES de cualquier acceso a DB para prevenir exposición de datos sensibles. Patrón validado en SF-4.1-S1 y replicado en este Sprint.

### Patrón 2: Upsert por coincidencia con aislamiento de userId

**Ubicación**: `app/api/import/prompts/route.ts` líneas 203-213

```typescript
const existing = await prisma.prompt.findFirst({
  where: {
    userId: userId,
    OR: [
      { id: promptData.id },
      { title: promptData.title },
    ],
  },
})
```

**Lección**: El filtrado por userId en la búsqueda de existentes garantiza que solo se reemplacen prompts del mismo usuario, nunca de otros usuarios.

### Patrón 3: Normalización de nombres para prevenir duplicados

**Ubicación**: `app/api/import/prompts/route.ts` líneas 75-82

```typescript
function normalizeName(name: string): string {
  return name.trim().toLowerCase()
}

function createSlug(name: string): string {
  return normalizeName(name).replace(/\s+/g, "-").replace(/[^a-z0-9-]/g, "")
}
```

**Lección**: Normalización (trim + lowercase) previene duplicados por case (ej: "GPT-4" vs "gpt-4"). Implementa decisión D-06.

### Patrón 4: Transaccionalidad en operaciones N:M

**Ubicación**: `app/api/import/prompts/route.ts` líneas 267-297

```typescript
await prisma.$transaction([
  prisma.promptPlatform.deleteMany({ where: { promptId: existing.id } }),
  ...platformIds.map((id) =>
    prisma.promptPlatform.create({
      data: { promptId: existing.id, platformId: id },
    })
  ),
  // ... más relaciones
])
```

**Lección**: `$transaction` garantiza atomicidad en operaciones delete+create de relaciones N:M. Implementa decisión D-07.
