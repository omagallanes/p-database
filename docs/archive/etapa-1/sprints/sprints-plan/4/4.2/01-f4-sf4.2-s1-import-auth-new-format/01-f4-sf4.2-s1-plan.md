## 3. Alcance del Sprint

### Qué debe conseguir este Sprint

1. **Auth check como primera operación**: Importar `auth()` desde `@/lib/auth`; ejecutar antes de cualquier acceso a DB; retornar 401 sin sesión (patrón validado en SF-4.1)
2. **Filtrado por userId**: Asignar `userId = session.user.id` a todos los prompts importados; verificar ownership en upsert (solo reemplazar prompts del mismo usuario)
3. **Detección de formato**: Leer campo `version` del JSON; si `"2.0"` → usar parser v2.0; si ausente/`"1.0"` → usar parser v1.0 (compatibilidad)
4. **Parser v2.0**: Procesar arrays de nombres para relations N:M (platforms, categories, clientProjects, useCases, modelHints, tags); hacer upsert de entidades si no existen; crear relaciones en junction tables
5. **Parser v1.0**: Procesar campos legacy (platform, clientOrProject, useCase, modelHint como strings simples); crear entidades automáticamente si no existen; mismo comportamiento actual pero con auth + userId
6. **Upsert por coincidencia (D-02)**: Si prompt importado coincide con existente (mismo userId + ID o mismo userId + título), reemplazar el existente; si no coincide, crear nuevo
7. **Validación Zod**: Schema estricto para v2.0 (arrays de nombres, campos prePrompt/manualDeUso); schema flexible para v1.0 (campos string)
8. **No romper imports antiguos**: Imports en formato v1.0 deben seguir funcionando exactamente como antes (solo con auth + userId añadidos)

### Qué NO entra en este Sprint

- Modificar `app/api/export/prompts/route.ts` (ya completado en SF-4.1-S1)
- Implementar rate limiting (SF-4.3)
- Crear UI de importación (fuera de alcance; ya existe)
- Modificar `lib/auth.ts` o `middleware.ts` (ver `02-correcciones-autenticacion-sprints.md`: NO tocar sin justificación extrema)
- Tests E2E de import (SF-5.1)

## 5. Plan de acción

### Acción 1: Auth check como PRIMERA operación (seguridad crítica)

**Archivo**: `app/api/import/prompts/route.ts`  
**Qué se cambia**: Añadir import de `auth()` y ejecutar como primera línea del handler  
**Por qué**: Decisión D-04; patrón validado en SF-4.1; ver `conocimiento_tecnico_preventivo.md` §30  
**Código**:
```typescript
import { auth } from "@/lib/auth"

export async function POST(request: NextRequest) {
  try {
    // CRÍTICO: Auth check como PRIMERA operación
    const session = await auth()
    if (!session?.user?.id) {
      return NextResponse.json({ error: "Unauthorized" }, { status: 401 })
    }
    const userId = session.user.id
    // ... resto del handler
  }
}
```
**Precaución**: NO modificar `lib/auth.ts` ni `middleware.ts` (ver `02-correcciones-autenticacion-sprints.md`)

### Acción 2: Schema Zod para detección de formato

**Archivo**: `app/api/import/prompts/route.ts`  
**Qué se cambia**: Reemplazar `importSchema` actual (usa `z.any()`) por schemas tipados para v1.0 y v2.0  
**Por qué**: Validación estricta; detectar formato por campo `version`  
**Código**:
```typescript
// Schema base común
const promptBaseSchema = z.object({
  id: z.string().optional(),
  title: z.string(),
  description: z.string().nullable().optional(),
  body: z.string(),
  type: z.string().nullable().optional(),
  status: z.string().optional(),
  language: z.string().optional(),
  isFavorite: z.boolean().optional(),
  version: z.number().optional(),
  changelog: z.string().nullable().optional(),
  notes: z.string().nullable().optional(),
  prePrompt: z.string().nullable().optional(),
  manualDeUso: z.string().nullable().optional(),
})

// Schema v2.0 (nuevo formato con relaciones N:M)
const promptV2Schema = promptBaseSchema.extend({
  platforms: z.array(z.string()).optional(),
  categories: z.array(z.string()).optional(),
  clientProjects: z.array(z.string()).optional(),
  useCases: z.array(z.string()).optional(),
  modelHints: z.array(z.string()).optional(),
  tags: z.array(z.string()).optional(),
  // Legacy fields (compatibilidad)
  platform: z.string().nullable().optional(),
  clientOrProject: z.string().nullable().optional(),
  useCase: z.string().nullable().optional(),
  modelHint: z.string().nullable().optional(),
})

// Schema v1.0 (formato antiguo con campos string)
const promptV1Schema = promptBaseSchema.extend({
  platform: z.string().nullable().optional(),
  clientOrProject: z.string().nullable().optional(),
  useCase: z.string().nullable().optional(),
  modelHint: z.string().nullable().optional(),
  category: z.string().nullable().optional(),
  tags: z.array(z.string()).optional(),
})

const importV2Schema = z.object({
  version: z.literal("2.0"),
  exportedAt: z.string().optional(),
  prompts: z.array(promptV2Schema),
  categories: z.array(z.any()).optional(),
  tags: z.array(z.any()).optional(),
})

const importV1Schema = z.object({
  version: z.string().optional(),
  exportedAt: z.string().optional(),
  prompts: z.array(promptV1Schema),
  categories: z.array(z.any()).optional(),
  tags: z.array(z.any()).optional(),
})
```

### Acción 3: Detección de formato y routing

**Archivo**: `app/api/import/prompts/route.ts`  
**Qué se cambia**: Tras auth check, leer `body.version` y dispatch al parser correspondiente  
**Por qué**: Soportar ambos formatos sin romper imports antiguos  
**Código**:
```typescript
const body = await request.json()
const isV2 = body.version === "2.0"

if (isV2) {
  const data = importV2Schema.parse(body)
  await importV2(data, userId)
} else {
  const data = importV1Schema.parse(body)
  await importV1(data, userId)
}
```

### Acción 4: Implementar importV1 (compatibilidad con formato antiguo)

**Archivo**: `app/api/import/prompts/route.ts`  
**Qué se cambia**: Migrar lógica actual de import a función `importV1`, añadiendo userId y upsert  
**Por qué**: Mantener compatibilidad con exports antiguos (D-02)  
**Lógica**:
1. Importar categories del JSON (crear si no existen por slug)
2. Importar tags del JSON (crear si no existen por slug)
3. Para cada prompt:
   - Buscar existente por `userId + id` o `userId + title`
   - Si existe → upsert (reemplazar con datos importados)
   - Si no existe → crear con `userId` del usuario autenticado
   - Campos legacy (platform, clientOrProject, useCase, modelHint) como strings
   - Tags: crear relaciones en PromptTag

### Acción 5: Implementar importV2 (nuevo formato con relaciones N:M)

**Archivo**: `app/api/import/prompts/route.ts`  
**Qué se cambia**: Nueva función `importV2` que procesa arrays de nombres de relaciones  
**Por qué**: Consumir formato JSON v2.0 generado por export de SF-4.1  
**Lógica**:
1. Importar categories del JSON (crear si no existen por slug; manejar parent relationships)
2. Importar tags del JSON (crear si no existen por slug)
3. Para cada prompt:
   - **Upsert de entidades relacionadas**: Para cada nombre en `platforms`, buscar Platform por name (case-insensitive); si no existe, crear con slug normalizado
   - Mismo patrón para `categories` (ya importadas), `clientProjects`, `useCases`, `modelHints`
   - Buscar prompt existente por `userId + id` o `userId + title`
   - Si existe → upsert: actualizar campos + reemplazar relaciones N:M (deleteMany + create en junction tables)
   - Si no existe → crear con `userId` + crear relaciones en junction tables
   - Usar `$transaction` para atomicidad (D-07)

### Acción 6: Upsert por coincidencia (D-02)

**Archivo**: `app/api/import/prompts/route.ts`  
**Qué se cambia**: Lógica de búsqueda de prompts existentes antes de crear  
**Por qué**: Decisión D-02 — prompts existentes que coinciden son reemplazados  
**Lógica**:
```typescript
// Buscar existente
const existing = await prisma.prompt.findFirst({
  where: {
    userId: userId,
    OR: [
      { id: promptData.id },
      { title: promptData.title },
    ],
  },
})

if (existing) {
  // Upsert: actualizar + reemplazar relaciones
  await prisma.prompt.update({
    where: { id: existing.id },
    data: { /* campos actualizados */ },
  })
  // Delete existing relations + create new ones
  await prisma.promptPlatform.deleteMany({ where: { promptId: existing.id } })
  await prisma.promptCategory.deleteMany({ where: { promptId: existing.id } })
  // ... etc
} else {
  // Create new
  await prisma.prompt.create({
    data: {
      ...promptData,
      userId: userId,
    },
  })
}
```

## 7. Seguridad y no regresión

### Qué debe preservarse

- **Auth check como primera operación**: Ver `conocimiento_tecnico_preventivo.md` §30; mismo patrón que SF-4.1
- **Filtrado por userId**: Ver `conocimiento_tecnico_preventivo.md` §31; NUNCA acceder a DB sin verificar userId
- **No modificar lib/auth.ts ni middleware.ts**: Ver `02-correcciones-autenticacion-sprints.md`; 3 errores históricos documentados
- **$transaction para delete+create de relaciones N:M**: Decisión D-07; atomicidad garantizada
- **Zod validation**: Prevenir inyección de datos malformados

### Qué debe revisarse

- **Ownership en upsert**: Solo reemplazar prompts del mismo userId; nunca prompts de otros usuarios
- **Creación de entidades globales**: Platform, Category, etc. se crean si no existen; cualquier usuario autenticado puede crear (D-06)
- **Normalización de nombres**: trim + lowercase al crear entidades (D-06)

### Riesgos de regresión

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|--------------|---------|------------|
| Import v1.0 deja de funcionar | MEDIA | ALTO | Parser v1.0 replica lógica actual exactamente |
| Prompts se asignan a userId incorrecto | BAJA | CRÍTICO | Verificar `userId = session.user.id` antes de cualquier create |
| Relaciones N:M duplicadas en upsert | MEDIA | MEDIO | deleteMany antes de create en junction tables |
| Entidades duplicadas por case | BAJA | MEDIO | Normalización trim + lowercase (D-06) |

### Condiciones de seguridad críticas

1. **Auth check ANTES de cualquier acceso a DB** (seguridad crítica)
2. **Filtrado por userId en TODAS las queries** de lectura y escritura
3. **Upsert solo dentro del mismo userId** (nunca cruzar usuarios)
4. **NO tocar lib/auth.ts ni middleware.ts** (errores históricos documentados)

## 9. Riesgos o advertencias

### Incidencias previsibles

1. **Formato v2.0 no coincide exactamente con export**: Si el export de SF-4.1 cambia, el parser v2.0 debe actualizarse. Ver `app/api/export/prompts/route.ts` para formato exacto.
2. **Entidades con mismo nombre pero diferente case**: La normalización (trim + lowercase) previene duplicados, pero puede cambiar el nombre original. Documentar este comportamiento.
3. **Categories con parent en v2.0**: El export incluye `categories` como array de nombres simples, no con jerarquía. Si el export cambia para incluir jerarquía, el parser debe actualizarse.

### Dependencias sensibles

- **SF-4.1-S1 completada**: El formato JSON v2.0 está definido en `app/api/export/prompts/route.ts`. Este Sprint debe consumir exactamente ese formato.
- **SF-1.3 completada**: Junction tables existen en DB. Si no, el Sprint fallará.
- **Auth funcional**: `lib/auth.ts` y `middleware.ts` deben estar en estado correcto (ver `02-correcciones-autenticacion-sprints.md`).

### Limitaciones o alertas relevantes

- **Sin tests automatizados de import**: La validación es manual. Se recomienda añadir tests en SF-5.1.
- **Import v1.0 no crea entidades relacionadas**: En formato v1.0, los campos legacy (platform, clientOrProject, etc.) se guardan como strings. No se crean entidades Platform, ClientProject, etc. Esto es intencional para compatibilidad.
- **Rate limiting no implementado**: SF-4.3 pendiente. El endpoint de import es vulnerable a abuso automatizado hasta que se implemente.
