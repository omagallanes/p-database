## 3. Alcance del Sprint

### Que debe conseguir este Sprint
1. **Auth check en export**: Añadir `auth()` al inicio del handler GET de export; retornar 401 si no hay sesion valida
2. **Filtrado por userId**: Modificar la query de Prisma para filtrar prompts por `userId` del usuario autenticado (D-04)
3. **Include de relaciones N:M**: Actualizar el `include` de Prisma para cargar todas las relaciones N:M (platforms, categories, clientProjects, useCases, modelHints) con include anidado
4. **Formato JSON con relaciones N:M**: Transformar la respuesta para incluir arrays de nombres de relaciones en lugar de campos string simples (D-02)
5. **Incluir nuevos campos**: Añadir `prePrompt` y `manualDeUso` al JSON exportado (ya existen en schema desde SF-2.2)
6. **Mantener compatibilidad de estructura**: El JSON exportado debe mantener la estructura base `{ data: { prompts: [...] } }` para que el import pueda procesarlo

### Que NO entra en este Sprint
- Modificaciones al endpoint de import (SF-4.2)
- Rate limiting (SF-4.3)
- Endpoints de creacion inline para nuevos valores (SF-4.3)
- Cambios en PromptForm, PromptList o PromptFilters (Fases 2 y 3 completadas)
- Tests de import (corresponde a SF-4.2)

## 5. Plan de accion

### Accion 1: Añadir `auth()` check al inicio del handler GET
**Archivo**: `app/api/export/prompts/route.ts`

Insertar verificacion de autenticacion antes de cualquier logica de export, siguiendo el patron existente en otros endpoints protegidos (ver `app/api/prompts/route.ts:105-112`):

```typescript
import { auth } from "@/lib/auth"

export async function GET() {
  const session = await auth()

  if (!session?.user?.id) {
    return NextResponse.json(
      { error: "Unauthorized" },
      { status: 401 }
    )
  }

  const userId = session.user.id
  // ... resto de la logica
}
```

### Accion 2: Filtrar prompts por userId del usuario autenticado
**Archivo**: `app/api/export/prompts/route.ts`

Modificar la query `prisma.prompt.findMany` para incluir `where: { userId }`, garantizando que solo se exportan los prompts del usuario autenticado (D-04):

```typescript
const prompts = await prisma.prompt.findMany({
  where: {
    userId: userId,
  },
  // ... include y orderBy
})
```

### Accion 3: Actualizar include con todas las relaciones N:M
**Archivo**: `app/api/export/prompts/route.ts`

Reemplazar el include actual por uno completo que cargue todas las relaciones N:M con include anidado. Ver seccion 17 de `integracion-prisma-typescript.md` para el patron correcto:

```typescript
const prompts = await prisma.prompt.findMany({
  where: { userId },
  include: {
    platforms: { include: { platform: true } },
    categories: { include: { category: true } },
    clientProjects: { include: { clientProject: true } },
    useCases: { include: { useCase: true } },
    modelHints: { include: { modelHint: true } },
    tags: { include: { tag: true } },
  },
  orderBy: { createdAt: "desc" },
})
```

### Accion 4: Transformar respuesta para formato JSON con relaciones N:M
**Archivo**: `app/api/export/prompts/route.ts`

Transformar cada prompt para incluir arrays de nombres de relaciones en lugar de campos string simples. El formato debe ser coherente con D-02 (nuevo formato completo):

```typescript
const exportData = prompts.map((prompt) => ({
  id: prompt.id,
  title: prompt.title,
  description: prompt.description,
  body: prompt.body,
  prePrompt: prompt.prePrompt,
  manualDeUso: prompt.manualDeUso,
  type: prompt.type,
  status: prompt.status,
  language: prompt.language,
  isFavorite: prompt.isFavorite,
  version: prompt.version,
  changelog: prompt.changelog,
  notes: prompt.notes,
  usageCount: prompt.usageCount,
  lastUsedAt: prompt.lastUsedAt,
  createdAt: prompt.createdAt.toISOString(),
  updatedAt: prompt.updatedAt.toISOString(),

  // Relaciones N:M (nuevo formato)
  platforms: prompt.platforms.map((pp) => pp.platform.name),
  categories: prompt.categories.map((pc) => pc.category.name),
  clientProjects: prompt.clientProjects.map((cp) => cp.clientProject.name),
  useCases: prompt.useCases.map((uc) => uc.useCase.name),
  modelHints: prompt.modelHints.map((mh) => mh.modelHint.name),
  tags: prompt.tags.map((pt) => pt.tag.name),

  // Campos legacy (mantener para compatibilidad con imports antiguos)
  platform: prompt.platform,
  categoryId: prompt.categoryId,
  clientOrProject: prompt.clientOrProject,
  useCase: prompt.useCase,
  modelHint: prompt.modelHint,
}))
```

## 6. Validacion y pruebas

### Que debe validarse
1. **Auth requerido**: GET sin sesion activa retorna 401 con `{ error: "Unauthorized" }`
2. **Filtrado por userId**: Usuario autenticado solo exporta sus propios prompts; no se exportan prompts de otros usuarios
3. **Relaciones N:M en JSON**: El JSON exportado incluye arrays de nombres para platforms, categories, clientProjects, useCases, modelHints, tags
4. **Nuevos campos en JSON**: El JSON exportado incluye `prePrompt` y `manualDeUso`
5. **Estructura de respuesta**: El JSON mantiene estructura `{ data: { prompts: [...], exportedAt, version } }`
6. **Compatibilidad con import**: El formato exportado debe ser procesable por el endpoint de import (SF-4.2)

### Mecanismos existentes
- `npm run build`: Verificacion de compilacion Next.js
- `npm run lint`: ESLint
- `npm test`: Jest + React Testing Library
- Patron de `auth()` existente en `app/api/prompts/route.ts` como referencia
- Patron de include N:M existente en `app/(app)/prompts/page.tsx` como referencia

### Pruebas manuales requeridas
| Flujo | Accion | Resultado esperado |
|-------|--------|-------------------|
| Sin auth | Acceder a /api/export/prompts sin sesion | 401 Unauthorized |
| Con auth | Acceder con usuario autenticado | 200 OK con JSON de sus prompts |
| Multi-user | Crear prompts con user A y user B; exportar con user A | Solo prompts de user A en el JSON |
| Relaciones N:M | Exportar prompt con 2 platforms + 3 categories | JSON incluye arrays: `platforms: ["CHATGPT", "CURSOR"]`, `categories: [...]` |
| Nuevos campos | Exportar prompt con prePrompt y manualDeUso | JSON incluye ambos campos |
| Prompt sin relaciones | Exportar prompt sin platforms/categories | Arrays vacios: `platforms: []`, `categories: []` |

## 7. Seguridad y no regresion

### Que debe preservarse
- **Auth middleware**: `middleware.ts` protege rutas de aplicacion; API routes requieren auth manual (patron existente)
- **Ownership**: Cada usuario solo exporta sus propios prompts (filtrado por userId)
- **Zod validation**: No aplica en GET, pero PUT/POST mantienen validacion
- **Datos existentes**: No se modifican prompts en DB; solo se lee y transforma para export
- **Campos legacy**: Se mantienen en el JSON exportado para compatibilidad con imports antiguos (D-02)

### Que debe revisarse
- Que `auth()` se llama antes de cualquier acceso a DB
- Que el filtro `where: { userId }` se aplica correctamente
- Que el include N:M no causa problemas de rendimiento con volumen alto de prompts
- Que la serializacion de fechas (`toISOString()`) funciona correctamente

### Riesgos de regresion
| Riesgo | Probabilidad | Impacto | Mitigacion |
|--------|-------------|---------|------------|
| Export expone prompts de otros usuarios | BAJA | CRITICA | Verificar que `where: { userId }` se aplica siempre; test con multiples usuarios |
| Include N:M causa error si relaciones estan vacias | BAJA | MEDIA | Prisma retorna arrays vacios correctamente; verificar con prompt sin relaciones |
| Formato JSON incompatible con import existente | MEDIA | ALTA | Mantener campos legacy en el JSON; SF-4.2 debera manejar ambos formatos |
| Fecha serializacion falla | BAJA | MEDIA | Usar `toISOString()` como en SF-2.2 (patron validado) |
| Auth check olvidado | BAJA | CRITICA | Seguir exactamente el patron de `app/api/prompts/route.ts:105-112` |

### Advertencia de seguridad critica
Se detectaron problemas de seguridad en fases previas (acceso login y persistencia login documentados en `doc-plan/errores-ctrl/02-correcciones-autenticacion-sprints.md`). Este Sprint debe garantizar que:
1. El auth check es la PRIMERA operacion del handler, antes de cualquier acceso a DB
2. El filtrado por userId es OBLIGATORIO, no opcional
3. No se exponen datos de otros usuarios bajo ninguna circunstancia
4. La respuesta de error 401 no revela informacion interna del sistema

## 9. Riesgos o advertencias

### Incidencias previsibles
1. **Include N:M con muchos prompts**: Si un usuario tiene muchos prompts con muchas relaciones, la query puede ser lenta. Mitigacion: el plan Hobby de Vercel/Neon tiene volumen bajo-medio; si se detecta problema, se abordara en SF-4.3.
2. **Campos legacy nulos**: Algunos prompts pueden tener campos legacy (`platform`, `categoryId`) como `null`. La transformacion debe manejar `null` correctamente.
3. **Fechas en prompts antiguos**: Prompts creados antes de SF-2.2 pueden tener `prePrompt` y `manualDeUso` como `null`. Esto es esperado y debe manejarse correctamente.

### Dependencias sensibles
- **SF-1.3 completada**: Migraciones aplicadas; relaciones N:M existen en DB con seed data
- **SF-2.2 completada**: Campos `prePrompt` y `manualDeUso` existen en schema
- **SF-3.2 completada**: Filtros multi-seleccion funcionan; no afecta export
- **D-02 resuelta**: Formato export/import definido — nuevo formato completo con compatibilidad para imports antiguos
- **D-04 resuelta**: Auth en export/import definido — usuario solo exporta sus propios prompts

### Limitaciones
- Este Sprint no modifica el endpoint de import (SF-4.2)
- No se aborda rate limiting (SF-4.3)
- No se optimiza rendimiento de queries con volumen alto (se monitorizara)
