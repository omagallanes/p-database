**Comando**:

### Acción 3: Implementar rate limiting en middleware.ts

**Qué**: Modificar `middleware.ts` para añadir rate limiting a endpoints POST de API.

**Por qué**: D-08 establece que el rate limiting debe implementarse en middleware.ts como protección global antes de llegar a las API routes.

**Patrón de implementación**:
- Usar `@upstash/ratelimit` con `FixedWindow` strategy
- Límite: 20 requests por minuto por IP para endpoints POST
- Endpoints GET no limitados (lectura es menos costosa)
- Cuando se excede el límite: retornar 429 Too Many Requests con header `Retry-After`
- Usar IP del request como identificador (funciona en Vercel con `req.ip` o `x-forwarded-for`)

**Precaución crítica** (de `02-correcciones-autenticacion-sprints.md`):
- NO modificar la lógica de autenticación existente en middleware.ts
- NO añadir rutas públicas innecesarias
- NO cambiar la lógica de redirección
- SOLO añadir rate limiting como capa adicional antes de `NextResponse.next()`

**Estructura del middleware modificado**:
```typescript
import { auth } from "@/lib/auth"
import { NextResponse } from "next/server"
import { Ratelimit } from "@upstash/ratelimit"
import { Redis } from "@upstash/redis"

// Rate limiter: 20 requests/min por IP para POST endpoints
const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.fixedWindow(20, "60 s"),
  analytics: true,
})

export default auth(async (req) => {
  const isLoggedIn = !!req.auth
  const { pathname } = req.nextUrl

  // Rate limiting para endpoints POST de API
  if (req.method === "POST" && pathname.startsWith("/api/")) {
    const ip = req.ip ?? req.headers.get("x-forwarded-for") ?? "unknown"
    const { success, reset } = await ratelimit.limit(ip)
    
    if (!success) {
      return new NextResponse(
        JSON.stringify({ error: "Too many requests. Please try again later." }),
        {
          status: 429,
          headers: {
            "Content-Type": "application/json",
            "Retry-After": String(Math.ceil((reset - Date.now()) / 1000)),
          },
        }
      )
    }
  }

  // === LÓGICA DE AUTENTICACIÓN EXISTENTE (NO MODIFICAR) ===
  const isPublicRoute =
    pathname.startsWith("/auth/signin") ||
    pathname.startsWith("/auth/signup") ||
    pathname.startsWith("/auth/error")

  if (!isLoggedIn && !isPublicRoute) {
    return NextResponse.redirect(new URL("/auth/signin", req.nextUrl))
  }

  if (isLoggedIn && isPublicRoute) {
    return NextResponse.redirect(new URL("/", req.nextUrl))
  }

  return NextResponse.next()
})

export const config = {
  matcher: [
    "/((?!api|_next/static|_next/image|favicon.ico).*)",
  ],
}
```

- `middleware.ts` compila sin errores de TypeScript
- Lógica de autenticación existente NO modificada (verificar con `git diff`)
- Rate limiting solo aplica a POST endpoints de API
- GET endpoints no limitados

| Riesgo | Probabilidad | Impacto | Mitigación |

| Variables de entorno no configuradas en desarrollo | MEDIA | ALTO | Rate limiter debe manejar gracefully cuando vars no están configuradas (fallback: sin rate limiting en dev) |
| Auth check se rompe por cambio en middleware | BAJA | CRÍTICO | NO modificar lógica de auth; solo añadir rate limiting antes |

## 9. Riesgos y advertencias

### Incidencias previsibles

| Incidencia | Probabilidad | Impacto | Mitigación |
|------------|-------------|---------|------------|
| Upstash Redis no configurado en desarrollo | ALTA | MEDIO | Rate limiter debe tener fallback: si vars no están configuradas, no aplicar rate limiting (solo en producción) |
| `req.ip` es undefined en Vercel | MEDIA | ALTO | Usar `x-forwarded-for` header como fallback |
| Rate limiting demasiado agresivo | BAJA | MEDIO | Límite de 20 req/min es generoso; ajustar si es necesario |

### Dependencias sensibles

| Dependencia | Sensibilidad | Justificación |
|-------------|-------------|---------------|
| `middleware.ts` | CRÍTICA | Cualquier error rompe autenticación para toda la aplicación |
| `@upstash/ratelimit` | MEDIA | Nueva dependencia externa; requiere cuenta Upstash (free tier) |
| Variables de entorno | MEDIA | Credenciales de Redis deben protegerse |

### Advertencias operativas

1. **NO desplegar sin configurar Upstash Redis**: Si las variables de entorno no están configuradas, el middleware fallará. Implementar fallback para desarrollo.
2. **Probar auth después del cambio**: El cambio en middleware es la causa de los 3 errores históricos documentados. Probar login → acceso → creación de prompt manualmente.
3. **Rate limiting es global para POST**: Afecta a TODOS los endpoints POST de API (prompts, tags, categories, platforms, import, etc.). Esto es intencional (D-08: protección global).
4. **Free tier de Upstash**: 10,000 commands/day, suficiente para desarrollo y producción baja. Si el proyecto crece, considerar upgrade.
