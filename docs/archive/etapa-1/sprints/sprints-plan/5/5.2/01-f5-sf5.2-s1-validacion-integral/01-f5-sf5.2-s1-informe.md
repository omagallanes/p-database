## 5. Correcciones de TypeScript aplicadas

### Problema 1: Acceso dinámico a Prisma no type-safe

**Original**:
```typescript
const existing = await prisma[entityType as any].findFirst({...})
```

**Corrección**:
```typescript
let existing: { id: string } | null = null

switch (entityType) {
  case "platform":
    existing = await prisma.platform.findFirst({...})
    break
  case "clientProject":
    existing = await prisma.clientProject.findFirst({...})
    break
  // ... más casos
}
```

**Por qué**: TypeScript no puede inferir tipos con acceso dinámico `prisma[entityType]`. Switch statement permite type safety completo.

### Problema 2: Campo `type` puede ser null

**Original**:
```typescript
type: promptData.type,
```

**Corrección**:
```typescript
type: promptData.type ?? "USER",
```

**Por qué**: Schema de Prisma define `type String @default("USER")` (no nullable). Datos importados pueden tener `type: null`, causando error de TypeScript.

### Problema 3: Relación `categoryId` no existe en Prompt

**Original**:
```typescript
await prisma.prompt.update({
  where: { id: existing.id },
  data: { categoryId },
})
```

**Corrección**:
```typescript
await prisma.$transaction([
  prisma.promptCategory.deleteMany({ where: { promptId: existing.id } }),
  prisma.promptCategory.create({
    data: { promptId: existing.id, categoryId },
  }),
])
```

**Por qué**: Schema usa relación N:M `PromptCategory` (junction table), no campo `categoryId` directo en `Prompt`.

## 12. Conocimiento técnico reutilizable

### Patrón 1: Switch statement para acceso dinámico type-safe

**Descripción**: Cuando se necesita acceso dinámico a propiedades de Prisma, usar switch statement en lugar de `obj[key as any]` para mantener type safety.

**Código de referencia**:
```typescript
async function upsertEntity(
  entityType: "platform" | "clientProject" | "useCase" | "modelHint",
  name: string
): Promise<string> {
  let existing: { id: string } | null = null
  
  switch (entityType) {
    case "platform":
      existing = await prisma.platform.findFirst({...})
      break
    case "clientProject":
      existing = await prisma.clientProject.findFirst({...})
      break
    // ... más casos
  }
  
  if (existing) return existing.id
  
  let created: { id: string }
  
  switch (entityType) {
    case "platform":
      created = await prisma.platform.create({...})
      break
    // ... más casos
  }
  
  return created.id
}
```

**Lección**: TypeScript no puede inferir tipos con acceso dinámico. Switch statement preserva type safety y previene errores en build.

### Patrón 2: Null handling para campos no nullable

**Descripción**: Campos de Prisma definidos como `String @default("VALUE")` no son nullable. Datos externos pueden tener `null`, requiring null coalescing.

**Código de referencia**:
```typescript
await prisma.prompt.create({
  data: {
    type: promptData.type ?? "USER",  // ✅ Null coalescing
    status: promptData.status ?? "DRAFT",
    language: promptData.language || "es",
  },
})
```

**Lección**: Siempre usar `??` o `||` para campos no nullable cuando se reciben datos externos (import, API, etc.).

### Patrón 3: Junction tables requieren operaciones explícitas

**Descripción**: Relaciones N:M con junction tables (ej: `PromptCategory`) no pueden actualizarse con campo directo (`categoryId`). Requieren operaciones explícitas en la junction table.

**Código de referencia**:
```typescript
// ❌ INCORRECTO: categoryId no existe en Prompt
await prisma.prompt.update({
  where: { id: promptId },
  data: { categoryId },
})

// ✅ CORRECTO: Usar junction table explícitamente
await prisma.$transaction([
  prisma.promptCategory.deleteMany({ where: { promptId: promptId } }),
  prisma.promptCategory.create({
    data: { promptId: promptId, categoryId },
  }),
])
```

**Lección**: Inspeccionar schema de Prisma para identificar junction tables. Usar operaciones explícitas en la junction table, no campos directos.
