## 12. Conocimiento técnico reutilizable

### Patrón 1: Planificación detallada antes de implementación

**Descripción**: Crear un plan de acción detallado antes de implementar tests permite:
- Identificar claramente qué tests se necesitan
- Definir criterios de aceptación medibles
- Estimar esfuerzo y priorizar
- Evitar duplicación de trabajo

**Aplicabilidad**: Patrón recomendado para Sprints de testing complejos. El plan de F5-SF5.1-S1 puede usarse como template para futuros Sprints de ampliación de tests.

### Patrón 2: Verificar baseline de tests antes de añadir nuevos

**Descripción**: Antes de añadir tests nuevos, ejecutar `npm test` para verificar:
- Tests existentes pasan (o identificar fallos pre-existentes)
- Infraestructura de testing funciona (Jest, mocks, etc.)
- No hay regresiones introducidas por cambios anteriores

**Código de referencia**:
```bash
npm test -- --listTests  # Verificar qué tests existen
npm test  # Ejecutar todos los tests existentes
npm test -- --coverage  # Verificar cobertura base
```

**Aplicabilidad**: Patrón obligatorio antes de cualquier Sprint de testing.

### Lección 1: Documentar incluso lo no implementado

**Lección**: Aunque los tests no se implementaron en este Sprint, se documentó detalladamente el plan de implementación. Esto permite que el siguiente Sprint retome el trabajo sin perder contexto.

**Aplicabilidad**: Cuando algo queda pendiente, documentar EXACTAMENTE qué falta, por qué, y cómo debe implementarse. No dejar "deuda técnica" sin documentación.

### Lección 2: Tests fallidos pre-existentes deben documentarse

**Lección**: Los 3 tests fallidos de PromptList.test.tsx (ViewModeProvider) son pre-existentes (SF-3.1). Deben documentarse para:
- No confundirlos con fallos nuevos
- Planificar su corrección en Sprint futuro
- Evitar que se acumule deuda técnica de testing

**Aplicabilidad**: Siempre documentar tests fallidos pre-existentes en informes de Sprint.
